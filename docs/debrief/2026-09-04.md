## Bait answer

*"Put the credentials in `.mcp.json` `env` so the server just works for everyone who clones."*

Wrong twice over, and today's build shows both. First the obvious half: `.mcp.json` is committed, so a literal token is a leaked token — the fix is `${VAR:-default}` expansion with the secret living in gitignored `.env`. But the subtler half is what MUFF actually hit: `env` in `.mcp.json` is the wrong place even for *non-secret* values that `.env` also sets. The server starts with `--env-file=.env`, and Node's `--env-file` never overrides a variable already in the process environment. `${FANTASY_PROVIDER:-}` expands to `""`, which counts as present — so `.env`'s `FANTASY_PROVIDER=sleeper` would be silently shadowed by an empty string. A key belongs in `.mcp.json` `env` only if `.env` never sets it; `YAHOO_LEAGUE_KEY` (optional, empty means auto-resolve) is the one that qualifies.

Second bait on the same exam item: *"shared team servers go in `~/.claude.json` so they don't clutter the repo."* That is user scope — one person, every project. The team's server belongs in project scope precisely so a clone carries it; the clutter cost is one 16-line file.

## What a teammate wouldn't know

1. **A missing `${VAR}` without `:-` does not fail — it passes the literal text `${VAR}` to the child process.** `claude mcp list` prints a warning and starts the server anyway, which means a misspelled variable name shows up as a Yahoo 401 or a "league not found", far from the config that caused it. Always give a default, even an empty one, so the failure mode is at least an empty string you can reason about.

2. **A stdio server inherits Claude Code's entire environment, so the `env` block is mostly unnecessary.** `FANTASY_PROVIDER=sleeper SLEEPER_LEAGUE_ID=… claude` flips the provider with no config edit at all. `env` is for explicit overrides and expansions, not for "passing variables through" — they already pass through. This is also why the shadowing bug above is easy to introduce: adding a key to `env` feels like plumbing but is actually a precedence decision.

3. **The approval for a checked-in server is recorded in `.claude/settings.local.json`, not `~/.claude.json`.** The doc says "per user"; the specific file matters because `settings.local.json` is gitignored by this repo's `.gitignore`, and if it weren't, one person's approval would ship to everyone — defeating the reason Claude Code asks in the first place (a committed file can start processes).

Small and real: `.mcp.json` landed in the *debrief* commit (`27777ef`) rather than the MUFF-55 commit because it had been staged earlier for the secret scan (`git grep` only sees tracked/staged files) and was still in the index when the debrief was committed. `git log -- .mcp.json` tells the truth; the commit message doesn't. Worth a `git status` before any commit that isn't `git commit <paths>`.

**Answer to the ticket's debrief question:** a tool is model-controlled (the model decides to call it, pays a round-trip, gets a payload); a resource is application-controlled (the client attaches it up front). A `league_summary` resource would put those in context before the first turn — logged as MUFF-56, not built.
