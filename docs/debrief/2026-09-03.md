## Bait answer

*"Recurring procedures belong in CLAUDE.md so Claude always follows them."*

Wrong, and today's artifact shows why: the debrief procedure is ~40 lines that matter only once per build day. In CLAUDE.md it would cost tokens in **every** session and could take no arguments. As a skill it loads on demand, accepts `$ARGUMENTS` (with `argument-hint` teaching the invoker what to pass), declares its own tool scope, and — via `context: fork` — keeps its verbose work out of the session that invoked it. CLAUDE.md is for invariants that apply to *all* work; skills are for procedures you invoke.

Second bait on the same topic: *"commands and skills are the same thing with different folders."* A command is a prompt template expanded inline into the current conversation; a skill is a packaged workflow that can fork. `/run-evals` runs in your context; `/debrief` doesn't.

## What a teammate wouldn't know

Two things this skill's own first run made concrete:

1. **`context: fork` inherits the conversation but not vice versa.** The fork arrived already knowing the day's context — no re-explaining — yet the full branch diff, the memory-file reads, and a Linear API round-trip it made to find the exam mapping never landed in the main session. Only the final report comes back. That's the whole reason the skill exists: the diff read is the expensive part, and the invoking session never pays for it.

2. **`allowed-tools` is pre-approval, not a sandbox.** The listed tools run without permission prompts, but the fork could still reach tools *outside* the list (grep via Bash, a Linear MCP read) — those simply route through the normal permission system instead of being hard-blocked. So `allowed-tools` shapes the skill's happy path and removes prompt friction; it is not the enforcement boundary the ticket's "blocked by allowed-tools" verify-step implied. If a skill must *never* write source, the real guarantees are the permission system and review — not the frontmatter alone.

Also small but real: `$ARGUMENTS` substitutes to an empty string when nothing is passed, so a skill body has to spell out the no-args behavior itself ("if none were given, infer them") — the harness won't prompt for missing arguments.

## Addendum

Second `/debrief` run today (no new commits since the entry above — the branch is still just `177646e`), which exercised the one path the first run couldn't: the idempotency guard. Two additions:

1. **Same-day reruns are the skill's job to handle, not the harness's.** Nothing stops a skill from being invoked twice; a forked skill also can't rely on remembering a prior run (a later session's fork inherits *that* session, not this one). The only reliable guard is the one written into the skill body — check whether `docs/debrief/YYYY-MM-DD.md` exists and append instead of overwrite. This run proved the guard works: file found, entry preserved, addendum appended.

2. **Bash `allowed-tools` globs are prefix patterns, and flags ride along.** `/run-evals`'s `Bash(npm run eval*)` pre-approves not just `npm run eval` but `npm run eval -- --live` — the glob matches the whole command string. Convenient here (the `--live` variant is the point of the `argument-hint`), but worth knowing when writing patterns for commands where extra flags change the blast radius: the glob doesn't distinguish "the safe invocation" from "the same binary with a scarier flag".
