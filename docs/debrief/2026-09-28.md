## Task statement touched

- **Runtime boundary:** the digest Lambda is stateless and lives for seconds; a WhatsApp Web session needs persisted encryption keys on disk and an open WebSocket. Those are incompatible shapes, so delivery is split into two processes that never call each other and share only the thing they already share — the `JsonStore`. Same reasoning as the digest being a *workflow* and the MCP server being a *process boundary*: put the seam where the runtime constraint is, not where the feature request is.
- **Failure isolation:** `enqueueWhatsApp()` never throws (pinned by the test), the drain loop never throws out of a record, and a failed poll can't block or retry the text. A WhatsApp outage costs the league WhatsApp, never Telegram.
- **Escalation to a human:** the sender's three failure modes that need a person (needs pairing, logged out, send failed) go to the admin's *private* Telegram chat — the channel guaranteed up when WhatsApp isn't — with the exact fix ("flip `outbox/…` back to `pending`").
- **Observability:** `whatsapp_queued` on `MUFF_RUN` means "the record was written", and only that; delivery gets its own `MUFF_WA` line from the process that actually did it.

## Bait answer

*"Add WhatsApp as another delivery step in the digest Lambda — it's one more `await sendMessage()` after Telegram."*

Wrong because the Lambda can't hold the session: no persistent disk for `WA_AUTH_DIR`, a cold handshake every Tuesday, and a pairing flow nobody is awake for at 7am — and that cold, bursty shape is exactly what trips WhatsApp's automation heuristics. The second-order bait is *"then use SQS between them."* One message a week doesn't need a queue service; the store is already the cross-process seam for fixtures, history and the run archive, and a keyed, mutable JSON record gives you idempotency for free (re-sending a week overwrites its record).

Smaller bait: *"`whatsapp_queued: true` in CloudWatch means it posted."* It doesn't — it's the hop before the hop. The doc's failure-mode table exists because "delivered" now has two answers.

## What a teammate wouldn't know

1. **There is no legitimate way to post into an existing WhatsApp group.** The official Cloud API can message individuals or groups *it* created; it cannot join the league's chat. The only thing that can post is a *member*, so the sender is a linked device on a spare number via Baileys — which violates WhatsApp's ToS. The design mitigation is organisational, not technical: the number must be a spare, so a ban costs nothing.
2. **The session lifecycle has a normal-looking failure and a fatal-looking one, and they're reversed.** A `515 restart required` close right after pairing is *expected* — reconnect with creds intact. A `401` means WhatsApp logged the device out: wipe `WA_AUTH_DIR` and re-pair, or you loop forever on dead creds. Pairing codes expire in about a minute, which is why the code is DM'd to the admin instead of printed on a host nobody is watching.
3. **The poll is post-only because votes are E2E-encrypted.** Decrypting a `messages.update` needs the original poll message's `messageSecret` kept around, plus a listener up all week. That forces daemon-only hosting and a sent-message store, so receipts still come from the Telegram poll.
4. **The chosen failure is a duplicate, not a lost message.** If the post succeeds but the status write fails, the next pass reposts and the admin gets a DM — at-least-once was picked deliberately because a repost is loud and a silent drop isn't.
5. **`JsonStore` roots itself at `process.cwd()/data` at import time**, so the test has to `chdir` into a scratch dir *before* dynamically importing `outbox.ts`, and delete `HISTORY_BUCKET` to force the file store. Related: `alert.ts` imports `telegram/bot.ts` dynamically because that module throws at load without a token — the sender should only need `TELEGRAM_BOT_TOKEN` when it actually alerts.

## Self-authored exam question

A scheduled, stateless workflow must deliver its output to a channel whose client requires persistent local state and a long-lived connection. Which design is most appropriate?

A. Open the connection inside the scheduled function each run and store its state in object storage.
B. Have the scheduled function write a durable record to shared storage, and run a separate long-lived process that consumes those records and reports its own delivery status.
C. Replace the scheduled function with a long-lived process so one runtime handles both generation and delivery.
D. Deliver from the scheduled function and mark the run failed if the channel is unreachable.

**Answer: B.** A separates the two runtime shapes at the seam where the constraint is, keeps the primary delivery independent of the fragile channel, and gives each hop its own status. A fights the platform, C couples generation to the channel's failure modes, and D lets a secondary channel fail the whole run.
